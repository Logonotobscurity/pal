# PAL Approval UI Implementation Summary

**Phase**: 3.3 — Approval UI and Flow

## Overview

Implemented PAL's approval dashboard and proposal viewing UI that allows users to review, approve, and reject action proposals generated by the Policy Engine. The UI follows the design mockup from PAL_ARCHITECTURE.md §29 and provides full visibility into the proposal lifecycle with provenance chain tracking.

## Key Design Decisions

### 1. Real-Time Updates: Polling vs WebSocket

**Decision**: Use polling (5-second interval) instead of Supabase Realtime.

**Rationale**:
- Simpler implementation for MVP
- No additional Supabase configuration required
- Adequate for approval flow (not high-frequency updates)
- Easy to upgrade to Realtime later without UI changes
- Proper cleanup with cancellation flag

**Future**: Upgrade to Supabase Realtime in Phase 4 (Task 4.3)

### 2. Edit Functionality: Placeholder

**Decision**: Create placeholder edit page, not full implementation.

**Rationale**:
- Edit requires clarification flow integration
- Needs re-evaluation by Policy Engine
- Requires semantic agent to re-interpret modified intent
- Workflow agent must regenerate ActionPlan
- Out of scope for approval UI task
- User can reject and start new voice command instead

**Future**: Implement in future task with clarification flow

### 3. Version-Aware Approvals

**Decision**: Pass `proposal.version` to approve/reject API endpoints.

**Rationale**:
- Prevents race conditions (two approvers acting simultaneously)
- Server validates version matches before applying decision
- Stale approvals rejected with clear error message
- Implements optimistic locking pattern from §29

**Implementation**: ProposalCard passes `version` in request body

### 4. Exact Payload Display

**Decision**: Always show exact payload as JSON in UI.

**Rationale**:
- PAL_ARCHITECTURE.md §29 requirement: "The approval must show the exact payload"
- Never approve abstract actions - user must see exactly what will execute
- Transparency prevents unexpected behavior
- JSON format shows all parameters clearly

**Security**: No sensitive data should be in proposals (credentials stay server-side)

### 5. Evidence Chain Display

**Decision**: Show full provenance chain for every proposal.

**Rationale**:
- Traceability: User can trace decision back to speech input
- Trust: Clear evidence builds confidence in system
- Debugging: Helps diagnose incorrect interpretations
- PAL principle: Preserve provenance through entire chain

**Display**: Type badge + ID + source + URI (if available)

## API Integration

### Endpoints Used
- `GET /api/proposals` - List proposals with filters
- `GET /api/proposals/:id` - Get single proposal with decisions
- `POST /api/proposals/:id/approve` - Approve proposal
- `POST /api/proposals/:id/reject` - Reject proposal

### Request Format (Approve)
```json
{
  "reason": "Approved by user",
  "version": 1
}
```

### Request Format (Reject)
```json
{
  "reason": "User-provided rejection reason",
  "version": 1
}
```

### Error Handling
- Network errors: Show error message
- Version mismatch: Alert user about stale proposal
- Unauthorized: Redirect to login
- Refresh list after successful action

## Security Considerations

1. **Authentication**: All pages check user authentication, redirect to login if unauthorized
2. **Workspace tenancy**: All queries scoped to user's workspace via RLS
3. **Version checking**: Optimistic locking prevents race conditions
4. **No credential exposure**: UI never shows provider API keys or secrets
5. **Reason required**: Rejections must include human-readable rationale

## Performance Considerations

1. **Polling interval**: 5 seconds balances freshness vs server load
2. **Cleanup**: Proper useEffect cleanup with cancellation flags
3. **Conditional rendering**: Minimize re-renders with proper React patterns
4. **Lazy loading**: Could add pagination for large proposal lists (future)
5. **Memoization**: Could add React.memo for proposal cards (future optimization)

## Known Limitations

3. **Edit not implemented**: Placeholder only. Requires clarification flow integration.
4. **No proposal search**: Filter by status only. Could add text search later.
5. **No bulk actions**: One proposal at a time. Could add bulk approve/reject if needed.
